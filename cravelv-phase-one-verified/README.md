# CraveLV Phase One

CraveLV is a focused growth workspace for independent food truck businesses. This repository is the complete Phase One SaaS foundation: one application, one data model, one deployment configuration, and one tested setup path.

## Included

- Responsive marketing site and professional application workspace
- Account registration, login, logout, password hashing, and protected routes
- Multi-tenant organizations with explicit user memberships and tenant-scoped records
- Brand profiles that guide content voice and business identity
- AI-ready content studio with an immediately usable local generation mode
- Content drafts, scheduling, and publishing calendar
- Catering and event lead CRM with pipeline stages and values
- Customer engagement inbox and response workflow
- SQLAlchemy data layer that runs on SQLite locally and PostgreSQL in production
- Render Blueprint, environment template, production server, health check, sample data, and automated tests

## Run locally

Python 3.12 is recommended.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
flask --app wsgi:app seed-demo
flask --app wsgi:app run --debug
```

Open `http://127.0.0.1:5000`. The seeded demo account is:

- Email: `demo@cravelv.com`
- Password: `CraveDemo123!`

The demo command is optional; a new workspace can be created from the registration page.

## Test

```bash
pytest -q
```

The test suite covers health checks, tenant creation, route protection, authentication, lead creation, and cross-tenant data isolation.

## Deploy on Render

The repository root contains `render.yaml`. Render can create the web service and PostgreSQL database from that file as a Blueprint.

1. Push the contents of this folder to a GitHub repository. `render.yaml`, `requirements.txt`, and `wsgi.py` must remain at the repository root.
2. In Render, create a **Blueprint** and select that repository.
3. Review the generated web service and database, then apply the Blueprint.
4. Wait for `/health` to report `{"status":"ok","service":"cravelv"}`.

Render generates the production secret and injects the PostgreSQL connection automatically. No source changes are required between local SQLite use and production PostgreSQL.

## Environment

| Key | Required | Description |
| --- | --- | --- |
| `SECRET_KEY` | Production | Session signing secret; generated by Render |
| `DATABASE_URL` | Production | SQLite or PostgreSQL connection string |
| `APP_ENV` | No | `development` or `production` |
| `SESSION_COOKIE_SECURE` | Production | Set to `true` behind HTTPS |
| `AI_PROVIDER` | No | `demo` by default; integration seam for a live provider |
| `OPENAI_API_KEY` | Future | Reserved for live AI generation |

## Architecture notes

Every business-owned table carries an `organization_id`. Request-level tenant resolution verifies that the signed-in user has a matching membership before exposing data. PostgreSQL URLs are normalized for the psycopg driver, while local development defaults to an instance-scoped SQLite file.

The content studio intentionally uses deterministic, brand-aware generation in Phase One so the app works without external credentials. The provider variables and service boundary are ready for a live AI provider in the next milestone.

## Phase Two seams

The foundation is prepared for migrations, team invitations, OAuth/social account connections, background publishing jobs, live AI generation, Stripe subscriptions, asset uploads, and analytics. These are deliberately left outside Phase One so this release remains deployable and testable without third-party account setup.
